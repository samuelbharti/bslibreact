# Markup map

Two different things live in this kit, and they are pinned differently.

**Layout, page shell, and output components** reproduce bslib's or
shiny's own markup in TSX, so each one is pinned against a catalog
sample: HTML rendered live from the installed bslib and shiny, not a
committed file (see `docs/markup-catalog.md` and
`docs/decisions/0001-no-fixtures-live-ground-truth.md` at the repo root
for why). Render the catalog from the repo root with
`Rscript tools/markup/render-r.R --out .cache/markup/r.json` (or
`make markup`, which renders both languages); this package's own test
suite (`tests/global-setup.ts`) reads the result and re-renders it
automatically the moment it goes stale. Each component's own file
comment says which catalog sample it is pinned against.

**Input widgets** (`SliderInput`, `SelectInput`, and the rest in
`src/inputs/`) do not reproduce any markup at all. Every one of them is
`HostedInput`, hosting one `output$<id>_ui <-
renderUI({ <the parent's own call> })` the app's own `app.R` defines,
under an `_ui`-suffixed name different from the widget's own input id
(see "Why widgets are hosted instead of rebuilt" in `docs/porting.md`
for why the two names must differ). There is nothing to pin, since the
widget's HTML comes from R at runtime, not from TSX. See
`docs/porting.md` for why this changed from an earlier,
markup-reproducing approach, and
[posit-dev/shinyreact#286](https://github.com/posit-dev/shinyreact/issues/286).

Not yet built as a reusable kit component: `navset_card_tab`/
`navset_pill` (the card-embedded tab styles, as opposed to the navbar's
own tab strip above), a generic `Accordion`/`AccordionPanel`
(recount-explorer's Browse tab hosts its one accordion as an
app-specific block instead, since no other port needs one yet),
`bslib::popover()` (every port that needs one so far has one or two
uses, always static with no reactive dependency, so it is cheaper to
host the whole popover call through the `uiOutput` escape hatch than to
build a component around Bootstrap's popover JS init). `plotly` still
has no dedicated component (use `WidgetOutput` for it; a dedicated
component is only worth it if one needs its own props) -- `reactable`
did get one (`ReactableOutput`, added for tahoe-explorer, which hosts
11 reactable tables across 6 modules): unlike plotly, a plain
`reactable::reactableOutput()` dump showed two real differences from
`WidgetOutput`'s generic shape, not just a class name -- a
`data-reactable-output` attribute reactable's own JS reads to find its
mount point (used by `reactable::updateReactable()`, e.g. row-selection
proxies), and a `width:auto;height:auto` default instead of
`WidgetOutput`'s `100%`/`400px`. Add each one the same way, when the
app that needs it needs it: add a sample to pkg-r's (and pkg-py's)
catalog, run `make markup`, read the rendered sample, write the
component against it, and add a markup test that reads it back through
`tests/catalog.ts`.

## Input widgets

Every row here is `HostedInput`, called by the named export; the name
is only there for readability at the call site
(`<SliderInput id="lfc_ui" />`), it carries no widget-specific props of
its own. The R side always looks the same:
`output$<id>_ui <- renderUI({ <the R call, unchanged> })`. The `_ui`
suffix matters: it keeps the output's own id different from the
widget's own input id (`lfc`), so the two don't collide in the DOM
(see `docs/porting.md`, "Why widgets are hosted instead of rebuilt").

| `shiny::sliderInput()`     | `SliderInput`                                                                                                                                                                               |
| `shiny::selectInput()`     | `SelectInput`                                                                                                                                                                               |

| `shiny::radioButtons()`    | `RadioButtons`                                                                                                                                                                              |

| `shiny::textAreaInput()`   | `TextAreaInput`                                                                                                                                                                             |

Verified directly, with a real running app: a hosted `sliderInput()`
becomes a real ionRangeSlider, a hosted `selectizeInput()` becomes real
selectize, both arrive at the server with their initial value on
connect, and `updateSliderInput()` from the server still moves the
hosted widget afterward.

Not yet built this way, still hand-hosted with their own markup (see
below): `checkboxGroupInput` (recount-explorer's own accordion block),
`dateRangeInput`, `input_task_button`, a range `sliderInput()`. Try
`renderUI()` + `HostedInput` for these first, the same as everything
else in this table; fall back to hand-written markup only if that
specific widget turns out not to work through `renderUI()`, and say why
in the component's own comment.

## Widgets that still write their own markup by hand

Not every hosted element can go through `output$<id>_ui <- renderUI()`:
something mixed into markup the client itself owns, a hosted tab link
that is one `<li>` among React-rendered siblings, cannot be swapped in
as a whole `renderUI()` output. `NavbarTabStrip` and `LayoutSidebar` are
the two cases in this kit: each writes its own markup by hand and binds
it to Shiny itself, through `useBoundScope` (`src/bind/useBoundScope.ts`)
rather than `HostedInput`'s own `renderUI()`-based binding. Reach for
that pattern again only when a widget genuinely cannot be its own
`renderUI()` output, and say why in the component's own comment; this
kit does not keep a generic host for it any more (see `docs/porting.md`).
